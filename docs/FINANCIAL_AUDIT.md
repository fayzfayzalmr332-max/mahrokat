## 1) الخلاصة التنفيذية

تم فحص كامل مسارات الحساب (الديون/السداد/الأرصدة/كشوف الحساب/التقارير اليومية
والشهرية) وضُبْطت الدوال الحسابية لتصبح:
- **زمنية حاسمة** (لا تداخل أرصدة ولا قلب حسابي حتى لنفس الثانية).
- **ذرّية ضد التكرار** (لا تسجيل مزدوج تحت سباق Race Conditions).
- **دقيقة على الأعداد العشرية** (Decimal نقية بلا أخطاء عائمة).
- **متزامنة زمنياً** مع توقيت المحطة (TIMEZONE_OFFSET) لا توقيت الخادم.

**قبل التدقيق: 82 اختباراً ناجحاً — بعد التدقيق: 117 اختباراً ناجحاً (صفر إخفاقات).**

## 3) التحصينات المنهجية المضافة

1. **ترتيب زمني حاسم** (`created_at.desc, id.desc`) في: `get_activity`، `today_summary`،
   `recent_payments`، `customer_stats`، `list_account_entries`، `account_stats` —
   فلا تتناوب النتائج لعمليتين بنفس الثانية (يحسّن موثوقية `/undo` وسجل العميل).
2. **مكافحة التكرار الذرّي**: `add_transaction` تقبل `external_ref` وتُدرج عبر
   `on_conflict=external_ref` + `Prefer: ignore-duplicates` (القيد موجود من الترحيل 003).
   مفتاح التفرد `_idempotency_ref(عميل/نوع/مبلغ/نافذة 5د)` يمنع التسجيل المزدوج حتى
   عندما يتجاوز طلبان متزامنان حارس ما قبل الإدراج. وعند قواعد قديمة بلا عمود يتراجع
   آلياً إلى الإدراج البسيط (يُكتشف مرّة واحدة).
3. **رفض القيم غير المحدودة**: `to_decimal` ترفض `NaN/Infinity` صراحةً قبل `quantize`
   (NaN تجتاز مقارنات الحجم، وquantize على Infinity يرمي نوعاً مختلفاً).
4. **دعم الفاصل العشري العربي «٫»** في `to_decimal` إضافةً للفاصلة الغربية.
5. **دفتر الأستاذ التراكمي**: `get_ledger(customer_id)` يعيد الحركات **من الأقدم حتى
   الأحدث** مع **الرصيد التراكمي بعد كل حركة** عبر view `v_customer_ledger`
   (الترحيل 005، window sum على `created_at, seq`) مع مسار حساب محلي مطابق عند غيابه.
6. **الطوابع الزمنية لحظية**: `now_utc()` تُلتقط وقت الإدراج مباشرة (بلا تجميد/تأخير)؛
   العرض المحلي عبر `TIMEZONE_OFFSET` فقط، وكل التحديثات المؤقتة تُستخرج من ساعة حية.

## 4) حالات الإجهاد المغطاة آلياً

- **عشوائية (Fuzz)**: 500+ قيمة عشرية عشوائية بمنازل متعددة → دقة منزلتين دائماً.
- **مبالغ ضخمة**: حدود `DECIMAL(15,2)` يقبلها، وما فوقها يُرفض؛ مجموع 3×`3333333333333.33` = أقصى حد بلا فيضان.
- **أخطاء عائمة**: جمع 1000 × `0.01` = `10.00` بالضبط.
- **قاعدة فارغة**: تقارير اليوم/الشهر تُعيد أصفاراً **بدون** قسمة على صفر.
- **نفس الثانية**: ترتيب حاسم عبر `(created_at, id)` يمنع قلب الحساب.
- **سباق الإدراج**: مفتاح التفرّد نفسه + upsert ذرّي؛ محاكاة تكرر → صف واحد فقط.
- **مدخلات خاطئة**: سلبية/صفر/نوع غير صالح/NaN/Infinity → `ValueError` موحّد.

## 5) الترحيل المطلوب على قاعدة البيانات

شغّل `migrations/005_running_ledger.sql` من Supabase SQL Editor (آمن/Idempotent):
يضيف عمود `seq` رتيباً + فهرس + view `v_customer_ledger` مع الرصيد التراكمي.
**ملاحظة:** التطبيق يعمل بدون هذا الترحيل (مسار بديل محلي)، لكنه يُفعّل دفتر
الأستاذ المحسوب على مستوى قاعدة البيانات.

## 6) الاتساق المالي المؤكَّد

- إشارات الدفتر: دين «+» / سداد «−» (متطابقة مع قيد `ck_transactions_sign`).
- الرصيد = مجموع الحركات (عملية تبديلية)؛ التصفير عند تطابق المقبوضات/المدفوعات = `0.00` بالضبط.
- رصد `now_utc()` عند كل إدراج، والتقارير تقرأ «الآن» الحقيقي لحظياً.

# ⛽ ملحق: حساب «اللترات» كحساب مالي مستقل (الترحيل 006)

**الحالة: مكتمل — 43 اختباراً مخصصاً (`tests/test_fuel_ledger.py`) — المجموع الكلي: 160 اختباراً ناجحاً.**

## 1) الهيكل — جدول `fuel_ledger` معزول تماماً عن النقد
- `fuel_ledger(id, customer_id, fuel_type, liters, entry_type, note, external_ref, created_at)`.
- `fuel_type ∈ {mazot, benzine}` و`liters numeric(15,3)` (أجزاء اللتر: 0.5، 0.25…).
- قيد ذهبي `ck_fuel_liters_sign`: سحب (دين) «+» / إيداع (سداد) «−» — لا سطر بلا اتجاه.
- `UNIQUE(external_ref)` لممانعة التكرار الذرّية، فهارس كشف حاسمة
  `(customer_id, fuel_type, created_at desc, id desc)`، وView `v_fuel_balances`
  لأرصدة مازوت/بنزين لكل عميل، وAudit + RLS بنفس سياسة بقية الجداول.
- **لا علاقة إطلاقاً** بجدول `transactions` النقدي: عملية لتر لا تُحرِّك الليرات
  والعكس صحيح — العزلة مفروضة على مستوى الجداول ثم مثبتة باختبار
  `test_add_fuel_never_touches_transactions_table`.

## 2) ذكاء المعالجة النصية
- «دين محمد 50 لتر» / «دين خالد 12.5 مازوت» / «سدد علي 30 بنزين» → حركة وقود
  لا نقداً أبداً (الوقود يُحسم **قبل** أي تفسير نقدي).
- «حساب محمد لتر مازوت» → كشف لترات فقط؛ «حساب محمد» → كشف نقدي متكامل + قسم لترات.
- **خلل جوهري مُصلَح في التطبيع** (`normalization.py`): كانت النقطة العشرية
  تُستبدل بمسافة فيتفكك «12.5» إلى «12» و«5» ويُسجَّل **12 فقط** — سواء نقداً أو
  لترات! الآن يُحمى الفاصل بين رقمين (`.` و`٫`) بحارس ينجو من التطبيع ثم يُستعاد.

## 3) كشف الحساب المتكامل
- «حساب محمد» يعرض رسالة واحدة: 💳 الرصيد النقدي أولاً، ثم قسم
  ⛽ «رصيد اللترات (حساب مستقل عن النقد)» سطراً منفصلاً للمازوت والبنزين،
  ثم آخر الحركات — والأرصدة المنسيّة تُعرض كصفّر `0`.
- «حساب محمد لتر مازوت» → بطاقة وقود فقط بلا أي رقم نقدي.
- التراجع `/undo محمد` يقارن آخر حركة نقد بآخر لترات **زمنياً** ويحذف الأحدث
  (زر `undofuel:` — مُصلَح: كان النمط يستثنيه فكان زراً ميتاً).

## 4) هندسة الصمود
- `_to_liters`: Decimal ثلاثي منازل HALF_UP، رفض `NaN/Infinity` وصفر/سالب
  ونوع وقود مجهول، وسقف `numeric(15,3)` — بلا أخطاء عائمة (Fuzz 400 قيمة).
- Up ذرّي `on_conflict=external_ref` + فحص سباق يُعيد الصف الموجود ولا يسجّل ثانية.
- قاعدة قديمة بلا 006: رسالة صريحة «شغّل 006_fuel_liters.sql» عند التسجيل،
  والكشف النقدي يعمل بلا قسم وقود ولا انهيار.

**للنشر:** نفّذ `migrations/006_fuel_liters.sql` مرة واحدة في Supabase SQL Editor.
